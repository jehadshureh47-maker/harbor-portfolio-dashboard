# Dashboard

**What it is:** An interactive HTML dashboard that ingests a property portfolio's monthly Excel reports (bounced cheques, cheque clearance, collections, occupancy, etc.) and turns them into KPI cards, interactive charts, filterable tables, automatic data-quality checks, and cross-report consistency checks. Runs entirely client-side — no server, no data upload — the Excel file loads directly into the HTML page.

**Origin:** Built first for Awqaf and Al Naser Club. Haider (Harbor leadership) asked for it to be made scalable across all portfolios and connected Jehad to Harbor's Head of IT — the wider rollout is his mandate.

**Live portfolios:** Awqaf, Al Naser Club — both fully working, used monthly.

**In progress / pipeline:** Dubai Police (Diaa Ramadan), RTA (Ibrahim Sijer Daghman), National Bonds (Lorie Ann Torio), VIP (Ahmed Bassyoni / Jona De Leon), Dubai Court (Preethi).

**Files:**
- `Dashboard_v2.html` — live/production.
- `Dashboard_NavTrial.html` — staging/testing copy, kept in sync with v2.
- `Dashboard_DEMO.html` — scrubbed demo with synthetic data (Awqaf report types only so far).
- Standalone Data Quality Validator tool — used during onboarding to check a new portfolio's Excel structure before building.

**Onboarding a new portfolio:** (1) get one sample monthly report as-is, (2) review terminology/structure differences, (3) build + demo before final adoption. No changes required on the portfolio's side — the dashboard adapts to their file format.

Traced the architecture first: each of the 8 report tabs is rendered via `iframe.srcdoc = base64ToUtf8(EMBEDDED_DASHBOARDS[r.id])`, and `srcdoc` iframes inherit the parent's origin — so `localStorage` is shared between the shell and every report iframe, making per-report caching viable with plain `localStorage`, no cross-origin workaround needed. Each of the 8 embedded templates already has an unconditional `bootstrapInitial()` call at the bottom of its script that shows a baked-in demo snapshot by default — that was the natural hook point. Decoded all 8 templates (`al-bounced`, `al-clearance`, `al-collections`, `al-occupancy`, `request-count`, `new-lease`, `count-report`, `bounced-cheques`) out of `EMBEDDED_DASHBOARDS`, and applied an identical anchor-based patch to each: (1) a `__MD_REPORT_ID` constant (unique per template, matching its `EMBEDDED_DASHBOARDS` key) plus `__mdSaveToCache`/`__mdTryRestoreFromCache` helpers inserted right after the existing `window.__mdFreshness = {...}` line; (2) `handleFile(file)` widened to `handleFile(file, opts)`, with a save-to-cache call added right after the real parse succeeds (`onSheetChange(best)` for the 7 multi-sheet templates, `render(parsed)` for Occupancy's simpler single-sheet flow) — skipped when `opts.fromCache` is true, so restoring doesn't just re-save the same bytes back to itself; (3) the bottom-of-script `bootstrapInitial();` call changed to `if(!__mdTryRestoreFromCache()){ bootstrapInitial(); }`, so a real cached upload always wins over the demo snapshot, and the demo snapshot stays the fallback exactly like before if nothing's cached. Cache format: `{name, savedAt, data}` JSON in `localStorage` under `md_upload_cache_v1__<report-id>`, with the file bytes base64-encoded via a manual `Uint8Array`→`String.fromCharCode` chunked loop (avoids call-stack overflow on large files that `String.fromCharCode(...bytes)` would hit) and reconstructed back into a real `File` object on restore, fed through the exact same `handleFile` pipeline a live upload uses — so restored data goes through identical parsing/validation/rendering, including triggering the same `postMessage({__mdReportUpdated:true})` ping the parent shell already listens for to refresh Overview/Exec Summary/Compare. All localStorage writes wrapped in try/catch (quota-exceeded or private-browsing failures just skip caching silently, console.warn only — never breaks the live view). Verified: decoded+patched all 8 templates individually with `node --check` on every script block (clean), then re-encoded to base64 and swapped back into `EMBEDDED_DASHBOARDS` for v2/NavTrial/DEMO — did a byte-for-byte round-trip check confirming every re-embedded blob decodes back to exactly the patched source, plus a fresh `node --check` on all 3 production files' outer shell scripts and all 24 (8 reports × 3 files) re-embedded inner scripts. All green. Not yet added: a dedicated "clear cached upload" UI control — skipped for now since uploading a new file naturally overwrites the old cache, and adding a button would mean touching each template's HTML markup (more surface area) for a rarely-needed edge case; can revisit if it turns out to matter in practice.

**Month-over-month trend, 8/24:** Round 2 brainstorm item #2. The Exec Summary tab's Monthly/Quarterly/Yearly period selector already existed but was "purely presentational" (its own code comment said so) — Quarterly/Yearly always showed a static "needs more than one month of data" note, because nothing kept last month's numbers around once a new file was uploaded. Fixed by hooking into the exact place `portfolioSnapshot['awqaf']`/`portfolioSnapshot['al-naser']` already gets written with real computed totals (inside `renderExecSummaryAwqaf()`/`renderExecSummaryAlNaser()`, right after the Compare tab's snapshot capture) — added `saveMonthlyHistory(portfolioKey, snap)`, which stashes just the real totals (`totalCollected`, `bouncedAmount`, `bouncedCount`, `netCollected`, `bounceRatePct`) into `localStorage` under `md_monthly_history_v1__<portfolioKey>`, keyed by the `periodKey` (`YYYY-MM`, already being computed from `cc.date_min`/`co.date_min` for the Compare tab) so re-uploading the same month updates that entry instead of duplicating it, capped at the last 24 months. Nothing new is calculated — every stored number is copied straight from numbers the Exec Summary already displays. Built three real views on top of that history, all gated on having actual data (never a projection): (1) Monthly view now shows a small real bar-chart trend of the last 6 uploaded months' Total Collected and Bounced/At Risk, once 2+ months exist; (2) Quarterly/Yearly views sum the real months falling into each Jan–Mar/Apr–Jun/etc. or calendar-year bucket, and only render a comparison once 2+ buckets have data — a bucket missing some of its months (e.g. only July of Q3) is explicitly labeled "(2 of 3 months — partial)" rather than silently presented as a complete quarter; (3) the old static note is now conditional — it still shows the honest "needs more than one month" message when fewer than 2 real months exist for that portfolio, but disappears once real month-over-month data is available. Per Jehad's "use skills either way to help" instruction, ran `modern-web-guidance`'s accessibility guide before finishing (mandatory for client-side HTML/JS work per this project's own skill policy, hadn't been explicitly re-checked for this addition) — it flagged two real gaps: the new trend `<table>` had no `<caption>`/`scope="col"` (added, using a visually-hidden caption plus scoped headers), and the bar-chart `<svg>`'s only accessible info was per-bar `<title>` hover tooltips, which don't reach screen-reader users — added `role="img"` plus a full `aria-label` spelling out every month's real value on each chart. Neither fix was cosmetic; both came directly from the guide's DOs, not invented. Verified: unit-tested the new history functions in isolation (dedup-on-re-upload, per-portfolio separation, quarter/year bucketing including partial-bucket detection, 24-entry cap eviction, graceful-empty chart output) — 21/21 checks passed — then `node --check` on all 3 production files' script blocks (all clean), plus a byte-for-byte diff confirming the new trend-logic region is character-identical across v2/NavTrial/DEMO after rollout. **Keyboard shortcuts + What's New panel, 8/24:** Round 2 brainstorm item #4. Two new header buttons next to the theme toggle (wrapped together in a new `.header-actions` flex container): "What's New" (bell icon, small amber dot badge when there's an unseen entry) and "Shortcuts" (help icon). What's New is a hand-maintained `WHATS_NEW` changelog array — most-recent-first, dated groups — copied straight from this project's own real shipped-feature history (nothing aspirational or roadmap-flavored in it), shown in a dialog that reuses the existing `.hm-modal` shell from the heatmap day-detail popup. Seen/unseen tracked via `localStorage` (`motherDashboardWhatsNewSeen` = the latest entry's date), badge clears the moment the panel is closed. Shortcuts: `/` focuses search, `1`-`9` jump to the first 9 sidebar tabs (reusing the exact same ordered list `mdSearchNavTargets()` already computes for the search feature, so the two can never drift out of sync), `T` toggles theme, `P` prints the current tab if it's Exec Summary or Compare (silently does nothing on tabs with no print view, rather than a dead-feeling button), `?` opens the shortcuts help panel. All shortcuts are skipped while focus is in an input/select/textarea/contenteditable, while any dialog is open, or while a Cmd/Ctrl/Alt modifier is held — so they can never hijack normal typing or OS/browser shortcuts. Per Jehad's standing "use skills" instruction, ran `modern-web-guidance`'s accessibility guide before finishing — it didn't have a shortcuts-specific entry, but reviewing it surfaced a real WCAG 2.1.4 (Character Key Shortcuts) concern I hadn't built in: single-key, no-modifier global shortcuts must be able to be turned off, since they can misfire for speech-input or switch-device users. Added a persisted "Turn off keyboard shortcuts on this device" checkbox inside the Shortcuts panel itself (`motherDashboardShortcutsDisabled` in localStorage) — the global keydown handler checks it first, before any shortcut key is handled; the header Shortcuts button always still works to turn them back on, so there's no lockout. Verified: 9/9 unit tests passing on the seen/unseen badge logic and the digit-to-tab mapping (isolated from the DOM, `test_whatsnew_badge.js`), `node --check` clean on all 3 files' script blocks, and — after catching a real (if cosmetic) discrepancy where the rollout script wrote `—`/`–` escape sequences into NavTrial/DEMO instead of the literal em/en-dash characters typed directly into v2.html — fixed it and re-confirmed the patched region is character-identical across v2/NavTrial/DEMO, not just functionally equivalent.
